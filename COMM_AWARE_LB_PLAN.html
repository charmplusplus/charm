Communication-Aware GPU Placement

Should we build a new comm-aware load balancer or reuse one — and what should it actually do? Companion to GPU_LB_PLAN.html, Phase 6.

The problem this has to solve

On Delta, GreedyRefineCentralGPULB moved 32 of 64 pic2d chares and made the application ~52% slower — ~20 ms/iteration against 13.4 ms with migration disabled — and it stayed slower long after migration had finished. The lasting cost is therefore the assignment, not the move. The balancer traded a marginal compute gain (objGPU is about 0.1% of step time) for a ghost-exchange pattern that now crosses process and device boundaries, and nothing in its objective could see that it had done so.

Migration cost is not communication cost. The two are easy to conflate and often discussed together, but they behave completely differently. Migration cost is paid once, at the load-balancing step. Communication cost is paid every iteration, forever after. A migration-cost term can only make the balancer reluctant, and reluctance is indiscriminate: it penalises a move that improves locality exactly as much as one that destroys it. At best it preserves whatever locality the initial mapping happened to have — it can never create any. Because the pic2d regression persists in steady state, reluctance alone cannot fix it.

Why none of them can be adopted as-is

1. A partitioner's output is an arbitrary relabelling

METIS, Scotch and recursive bipartitioning all solve "cut this graph into k balanced parts." Nothing in that formulation says part 3 should be the part that already lives on PE 3. Run at every LB step, a partitioner therefore remaps nearly everything — which is precisely the failure mode we are trying to fix.

Scope this objection correctly. It holds for MetisLB (METIS_PartGraphRecursive, MetisLB.C:164), ScotchLB (SCOTCH_graphPart, ScotchLB.C:140), ScotchTopoLB (SCOTCH_graphMap, ScotchTopoLB.C:146) and ZoltanLB (LB_APPROACH="PARTITION", ZoltanLB.C:201). It does not hold for ScotchRefineLB, which seeds from the incumbent assignment as a first-class part of its formulation — and none of the four above call the part-remapping step that would fix them.

Nor are the mitigations "bolt-ons." Matching parts to PEs by maximum overlap is a maximum-weight bipartite matching on the overlap matrix, with a greedy 2-approximation that runs in O(E); the published penalty for skipping it is on the order of 5%. That is small next to pic2d's 52%, which means partitioner relabelling is probably not the dominant term in the regression we measured — the honest reason to extend the refinement balancer instead is objections 2–4, not this one. Keep the verdict; drop this objection's claim to being decisive.

2. They are flat over PEs; our problem is two-level

The GPU decision (which device, therefore which process) and the CPU decision (which PE inside that process) have different cost structures and different balance targets. A flat partitioner sees N interchangeable parts. On a 4-GPU node with 8 PEs per GPU, "PE 7 and PE 8" is a device boundary while "PE 6 and PE 7" is not, and a flat model cannot express that.

3. Edge weights are transport-blind

In every one of these, a cut edge costs the same wherever it lands. On a multi-GPU node the same logical edge spans four cost tiers that differ by orders of magnitude — a same-device exchange versus a cross-node RDMA staged transfer. None of the existing balancers consult the transport at all, and ScotchTopoLB, the only one whose model could express a hierarchy, hardcodes a 3D torus instead.

findTransferModeDevice does less than this document assumed. It is process-granular and returns three values, not four (conv-core/conv-rdmadevice.C:7-19): MEMCPY for same logical node, IPC for different logical node but same physical node, RDMA otherwise. Every intra-process pair — same device and cross device alike — collapses to MEMCPY. The T0/T1/T2 split has to come from elsewhere, as an explicit ordered predicate:

Tier tierOf(int src, int dst) {
    if (src == dst) return T0;                       // same PE — no message at all
    switch (findTransferModeDevice(src, dst)) {
      case MEMCPY: return gpu_device_id[src] == gpu_device_id[dst] ? T1 : T2;
      case IPC:    return T3;
      case RDMA:   return T4;
    }
}
// The ordering is load-bearing: the src == dst test must precede the call,
// and the gpu_device_id test only means anything inside the MEMCPY case.
4. Single load dimension, and it is the wrong one

ObjGraph sets CkVertex::compLoad = objData[v].wallTime — host CPU time only. The SM-normalised gpuTime that this whole branch exists to collect never reaches the graph.

Worse than the wrong dimension — a constant one. CkVertex::getVertexLoad() is MAX(compLoad, 0.1) (ckgraph.h:152). At pic2d's granularity every per-object load is far below 0.1 s, so every vertex weight the partitioners see is identical. Any A/B against MetisLB or RecBipartLB on this workload is measuring pure edge cut with uniform vertex weights, and reports a balance quality it did not actually compute. Fix or bypass the floor before drawing any conclusion from such a comparison.

Do not reach for ncon = 2. An earlier draft called METIS multi-constraint partitioning a good fit for carrying CPU and GPU as separate balance constraints. With our skew it is actively harmful: the GPU term is ~0.1% of step time, and multi-constraint partitioning enforces every constraint to the same tolerance, so METIS spends its freedom satisfying a dimension that cannot affect runtime and gives up cut quality to do it. For the startup mapper below, use ncon = 1 with a single scalar weight equal to the predicted per-object step-time contribution.

Verdict: extend GreedyRefineCentralGPULB; reuse ObjGraph, not a balancer. The refinement structure — an incumbent assignment, a per-object decision to stay or move, a tolerance governing how much improvement justifies a move — is the right shape for this problem and is exactly what the partitioners lack. What we are missing is a term in the objective, not a different algorithm. ObjGraph (src/ck-ldb/ckgraph.h) already does the tedious half: it converts LDStats::commData into per-vertex sendToList/recvFromList with message and byte counts, resolves object keys through the comm hash, and writes decisions back via convertDecisions. Reuse it for plumbing and keep our own placement logic.

Three defects in ObjGraph to fix before building on it

All three are in shared code that every graph LB in this tree inherits. Own them as step-3 prerequisites rather than discovering them as symptoms.

  • Multicast is not in the edge lists. An earlier draft said ObjGraph "handles multicast." It does, but in separate lists: only LD_OBJ_MSG reaches sendToList/recvFromList (ckgraph.C:78-83), while LD_OBJLIST_MSG goes to mcastToList/mcastFromList (ckgraph.h:161-162). A commCost() that walks only the first pair silently prices every multicast at zero.
  • vertices[-1] on a hash miss. ckgraph.C:79-83 takes from and to straight from stats->getHash() and indexes with them unguarded; the equivalent loop in BaseLB checks first. A chare that communicated and then died inside the instrumentation window corrupts the vector. Two lines: if (from < 0 || to < 0) continue;
  • The 0.1-second vertex-load floor described under objection 4 — decide deliberately whether the comm term's companion load term should inherit it. It should not.

A fourth, in our own code rather than ObjGraph: GObj indices and ObjGraph vertex indices coincide only over [0, n_migrateobjs), because the balancer's fill loop stops there. Size the GObj vector to stats->objData.size() and continue past non-migratable objects after charging them as background, so the two index spaces agree unconditionally.

Worth borrowing rather than adopting

  • RecBipartLB's RefineBoundary — a KL/FM gain-based boundary swap. Once a comm term exists, this is the natural inner refinement pass: it only considers objects on a partition boundary, which is where locality is actually won or lost, and it is cheap.
  • METIS as a startup mapper, not a balancer — see below.

The one place a partitioner genuinely fits

Objection 1 — that a partitioner remaps everything — costs nothing when nothing has been placed yet. At t = 0 an arbitrary relabelling is free.

pic2d currently builds its array with a bare CProxy_Patch::ckNew(n_chares_x, n_chares_y), so it gets DefaultArrayMap: a linearisation of the 2D index space blocked over PEs. For a 5-point stencil that is a reasonable but not good mapping — it gives long thin strips with a large surface-to-volume ratio rather than compact blocks.

So the division of labour is:

  • Startup: a partitioner (or, for a structured stencil, simply a 2D blocked CkArrayMap — cheaper and near-optimal) produces a communication-minimising initial mapping.
  • Every LB step after that: GreedyRefineCentralGPULB with a comm term maintains it, moving objects only when the load imbalance is worth the locality it breaks.

Neither half works alone. A good initial map with a locality-blind balancer is destroyed at the first AtSync — which is the regression we measured. A locality-aware balancer starting from a bad map spends every step climbing out of a hole it should never have been in.

What the balancer should do

The cost table

The same tiers as Phase 3's migration cost — but not the same numbers, and the place they diverge is T1. Tiers, not hard-coded values: the numbers are calibrated (see below). Each tier is a pair of constants, not one: a per-message fixed cost α and a per-byte cost β, applied as

tierCost(t, e) = alpha[t] * e.getNumMsgs() + beta[t] * e.getNumBytes();

T2Same process, different GPUPeer D2D copynear 01 / peer BW (~25 GB/s, PCIe)
T3Same node, different processCUDA IPChandle open + pull syncsame as T2

Three notes on the tier model.

Migration and communication diverge at T1 — do not share one number. For migration, T1 genuinely is a pointer handoff and genuinely is free: emigrateIntraProcess (cklocation.C:3081) ships raw element pointers with no PUP and no device copy, and it is gated on same CmiNode and hapiDeviceForPe(src) == hapiDeviceForPe(dst) (cklocation.C:3229-3237), returning before the export-and-pull path is reached. Ownership transfers, so nothing moves.

For communication it cannot work that way: a ghost exchange writes into a buffer the receiver already owns, so there is nothing to alias. CkDevicePersistent::get takes the MEMCPY branch (ckrdmadevice.C:234) and issues a full hapiMemcpyDeviceToDevice — on the same device, but a real copy of every byte. So T1's communication β is nonzero: on an A40 roughly βT2/28, HBM rather than PCIe. Reserve 0 for T0, the only tier that sends no message at all.

This is the one asymmetry between the two uses of the table, and it is structural rather than a calibration detail: migration can transfer ownership, communication cannot.

T2 and T3 share a β. Both are peer device-to-device copies over the same physical link; CUDA IPC does not make the wire slower. They differ in α — the handle open plus the synchronous pull wait — and nothing else. Modelling them as two bandwidth tiers double-counts a difference that lives entirely in the fixed term.

T4 is not host-staged, and the "2×" factor is not a host round trip. Nothing on this path copies to host memory. Cross-node communication is GPUDirect RDMA straight from the source device buffer. Cross-node migration does stage, but into a device buffer: dm->alloc_comm_buffer takes it from the device LB pool, the PUP packs the chare's scattered device allocations into it with D2D copies, and sendGPUMsg ships that contiguous region over GPUDirect (cklocation.C:3052-3072, 3272-3310). So the two-term shape is right for migration — pack, then ship — but the pack term runs at HBM speed and the ship term at network speed; neither is host bandwidth.

A genuinely host-staged path does exist in the source — ckrdmadevice.C:501, commented "use a naive host-staged mechanism" — but it is behind #if !CMK_GPU_COMM, and CMK_GPU_COMM is defined to 1 unconditionally at ckrdmadevice.C:53. It is dead code here. If it is ever revived for a non-GPUDirect machine layer, T4's constants have to become build-dependent — that fallback is roughly an order of magnitude worse and would change which moves are worth making.

T2 or T3 can silently collapse toward T4. When peer access is unavailable between two devices, the runtime falls back to a slower path and the cost jumps a tier with no change in the topology predicate. Probe cudaDeviceCanAccessPeer at calibration time and demote the tier explicitly rather than discovering it as an unexplained slowdown.

The tier for any (srcPe, dstPe) pair comes from the ordered predicate in objection 3 — findTransferModeDevice alone is process-granular and cannot split T1 from T2.

The objective

Charging communication to the PE that pays it, rather than summing it globally, is the right instinct: total edge cut is what a partitioner minimises, but what lengthens a step is one PE's inbox, and those differ whenever the cut is unevenly distributed. The first draft of the formula got the algebra wrong, though, in a way that matters.

Do not add maxima taken over different PEs. The drafted form was maxp(compp) + w · maxp(commp), which charges the compute peak of one PE and the communication peak of a different PE to the same imaginary processor. It over-counts whenever the two peaks are on different PEs — the common case — and it is not the makespan of any real assignment. Sum per PE first, then take the max. 
// Per-PE time, then the bottleneck over PEs:
peTime(p)  = cpuLoad(p)                       // Phase 1, overlap-adjusted by Phase 2
           + commWeight * commTime(p);        // new

cost(assignment) = max( max over groups g of gpuGroupLoad(g),   // separate resource
                        max over pe p     of peTime(p) );

// Send and receive run concurrently on a duplex link -- take the max, not the sum.
commTime(p) = max( sum over outgoing cross-PE edges of tierCost(tier(p, nbrPe), e),
                   sum over incoming cross-PE edges of tierCost(tier(nbrPe, p), e) );

The GPU-group term stays a separate max because it is a genuinely different resource; the CPU and communication terms do not, because they are both paid by the PE. Two further points on the inner sum:

  • Charge an edge once per endpoint, as max(sent, received). The earlier "an edge is charged once to each endpoint's PE" double-charges a duplex link the hardware runs concurrently. Accumulate sendCost(p) and recvCost(p) separately and combine with max. Keep the sum form behind a flag for the staged T4 path, where send and receive really do serialise through the host.
  • Put each tier's α on the end that pays it. For T3 the fixed cost is the receiver's pull wait, not the sender's — so αT3 belongs in recvCost. This is asymmetric and the code should say so.

Keep totalTierBytes = Σedges tierCost(e) as a diagnostic rather than an objective. It is the hop-bytes analogue, and it is the quantity that should fall when locality improves — which makes it the right sanity check for step 2's edge dump, and the wrong thing to optimise.

Scoring a candidate placement

double commCost(int objIdx, int candidatePe) {
  double c = 0;
  for (const CkEdge &e : vertices[objIdx].sendToList) {
    int nbrPe = (newPe[e.getNeighborId()] >= 0)   // placed already this pass?
                  ? newPe[e.getNeighborId()]      //   use the new decision
                  : oldPe[e.getNeighborId()];     //   else assume it stays put
    c += tierCost(tierOf(candidatePe, nbrPe), e);   // alpha*msgs + beta*bytes
  }
  // recvFromList likewise, accumulated separately -- combine with max(), not +
  // AND a third loop over mcastToList/mcastFromList; see below
  return c;
}

stats->to_proc already implements the placed/unplaced rule. The newPe/oldPe ternary above is exactly what to_proc holds during a central LB's assignment pass — it is seeded from the incumbent and overwritten as decisions are made. No new bookkeeping array.

Three things the drafted commCost gets wrong

  • It drops every multicast edge. sendToList/recvFromList carry only point-to-point LD_OBJ_MSG traffic. Add a third loop over mcastToList/mcastFromList, and charge a multicast sender once per distinct destination PE — dedupe over the destination list — rather than once per destination object. This is also the one place where per-edge byte weighting genuinely over-counts: a multicast to eight objects that happen to share a PE is one message on the wire, not eight.
  • It uses bytes only. With α and β per tier, use e.getNumMsgs() alongside e.getNumBytes(). At pic2d's 590 KB–5.9 MB payloads the α/β crossover falls inside the observed range at device bandwidths, so message count is not a rounding error. Charm++ already exposes _lb_args.alpha() and _lb_args.beta() — seed the cross-node tier T4 from them so existing tuning still applies.
  • It considers every PE as a destination. Restrict the candidate set: an object's legal destinations are the groups/PEs already hosting at least one of its ObjGraph neighbours, plus the globally lightest group as an escape hatch. This is the published fix for exactly this regression shape, it makes the comm term cheap to evaluate, and the escape hatch is what keeps a genuinely imbalanced run from freezing.
Ordering hazard — and the reason not to fix it with a comm-based sort key. A comm term inside a greedy loop is order-dependent: when object i is placed, some of its neighbours are not. Scoring against the peer's old PE is the standard treatment and a good prior, since most objects will not move.

An earlier draft proposed also reordering the sort key so that heaviest-communicating objects are placed first. Don't. Communication cost is non-monotone in the assignment — moving an object can reduce one PE's comm time and raise another's — so there is no ordering of objects by communication that a greedy pass can consume the way it consumes descending load. Keep Phase 1's max(load, cpuLoad) ordering, which is well-founded, and put the communication optimisation in a bounded boundary-refinement pass afterwards.

What the ordering change would have cost is also quantifiable, and it is small: longest-processing-time-first ordering guarantees a makespan within 4/3 − 1/(3m) of optimal, arbitrary order within 2 − 1/m. So abandoning load order risks at most about 1.5× in balance on 32 PEs — recoverable by a refinement pass, but there is no reason to pay it when the second pass is the better instrument anyway.

The refinement pass, promoted

RecBipartLB's RefineBoundary was filed above under "worth borrowing." Promote it to a scheduled step. A single-level refinement balancer — which is what this is — is specifically weak on long, thin partitions, and a KL/FM gain-based boundary pass is the cheapest available mitigation: it only touches objects on a partition boundary, which is exactly where locality is won or lost. Run it after the greedy assignment, in BFS order over the ObjGraph seeded from the heaviest object, and bound it so it cannot worsen the balance the packing pass achieved.

Calibrating the constants

Three options, in increasing order of fidelity and effort:

  1. Hard-code per architecture. Fragile, but a starting point. PCIe 4.0 measured at roughly 25 GB/s on Delta's A40s.
  2. Micro-benchmark at startup. One D2D copy per tier on the first LB step. The IPC handle-open cost measured here also feeds the deferred A-vs-C staged-versus-IPC switching decision.
  3. Learn from history. Record (bytes, tier, elapsed) for each actual transfer and fit. Most accurate, most machinery; defer.

Start with (2) — it is a few dozen lines and removes the per-machine fragility of (1). Two requirements on how (2) is run:

  • Fit two numbers per tier, not one. A zero-byte round trip gives α; a large payload gives β. Print α/β alongside the tier table under _lb_args.debug() so the crossover is visible against the observed edge byte counts.
  • Make it concurrent, not pairwise. A single idle-machine ping-pong systematically under-calibrates exactly the tiers the balancer exists to avoid, because the contention that makes T3 and T4 expensive only appears when many PEs transfer at once. For T2, have every GPU-bound PE issue its peer copy simultaneously and divide achieved aggregate bandwidth by the number of concurrent streams; for T3, have all PEs in a process pull at the same time. Calibrating on an idle machine tells you the tier ratios are mild, and then the balancer believes it.

Express the results as dimensionless ratios against T1 rather than absolute bandwidths — it makes the table portable and makes a miscalibration obvious by inspection.

commWeight, and why it should not be swept

The objective adds seconds of compute to seconds of communication, so commWeight is 1 by construction and the terms are directly comparable. Treat any need to deviate from 1 as evidence the tier calibration is wrong, not as a tuning opportunity.

The missing multiplier is not a weight — it is the epoch length. The drafted objective adds a per-iteration cost to a one-time cost with no conversion between them. Communication is paid every iteration until the next LB step; migration is paid once, at the step. The factor relating them is the number of application iterations the assignment will be in force — which Charm++ knows, because it is the AtSync interval. 
cost = max( maxGpuGroupLoad, max_p peTime(p) )   // per iteration
     + migrationCost / epochIterations;           // amortised over the epoch

// equivalently, and more readable in the assignment loop:
//   epochIterations * (per-iteration cost) + migrationCost
With the measured 25–240 μs migration cost and a typical LB period of 100 iterations, a per-iteration communication saving of a few microseconds already repays the move — which is the calculation the balancer currently cannot do at all.

So spend the third search dimension on something unknown, not on a quantity that has a derivation. The candidate worth sweeping is the communication-to-migration ratio, and even that has a published recipe: set it each step from measurement, as (inter-process communication time since the last LB step) / (measured migration time of the last LB step), clamped to a sane range with a fixed value on the first step. Keep a scalar override flag for experiments; make the default derived.

An alternative structure: balance as a constraint, communication as the objective

Worth stating because it addresses the root failure directly. The additive form is what let a 0.1% GPU term drive 32 migrations: any term in a weighted sum can dominate if the others are small enough. The constrained form cannot do that.

feasible(s)  :=  maxGpuGroupLoad(s) <= (1+eps) * avgGpuGroupLoad
             &&  maxPeCpuLoad(s)   <= (1+eps) * avgPeCpuLoad;

// among feasible solutions, minimise communication + amortised migration.
// if none is feasible, fall back to today's pure load objective.

Neither of the two closest published systems uses an additive weighted objective; both make load a hard tolerance and communication the thing minimised inside it. The existing A refine tolerance is already the right knob to reuse for ε. This is a larger change than adding a term, so it is not the first move — but if the additive form proves hard to tune, this is where to go, not to more weights.

Validation

Each step is measurable on its own; do not stack them before measuring.

  • Step 2, single GPU: edge dump shows 8 neighbours for every chare, not 4 for interior ones — pic2d's grid is periodic. An acceptance criterion of "4 per interior chare" would flag a correct graph as broken. Check the phi edges separately: those are 4-way.
  • Step 7 alone, no LB: blocked map versus DefaultArrayMap, migration disabled. Isolates the initial-mapping gain from everything else.
  • Steps 3–5, 4 processes × 8 PEs on Delta: the headline number is iteration time with the balancer against the 13.4 ms no-migration baseline. Migration count should fall well below 32/64, but count is a diagnostic — time is the result. Report totalTierBytes and max-per-PE comm time alongside it: if wall time improves and neither of those moved, the improvement came from somewhere else.
  • Regression: a genuinely imbalanced run must still migrate. A comm term that simply freezes everything in place is not a fix, and would look identical to success on pic2d, which is already balanced.
  • Rule out the frequency confound first. LB period is a variable this plan never named, and for a regular stencil the published answer is "balance once, early." Before attributing the 52% regression to the assignment at all, re-run the Delta case with exactly one LB invocation and compare. If a single invocation is most of the regression, the assignment is the problem and this plan is aimed correctly; if repeated invocations are, the cheaper fix is to stop calling the balancer.
Scope step 7 honestly. The surface-to-volume argument for a 2D blocked map over DefaultArrayMap's strips is real, but at pic2d's actual configuration — 64 chares over 4 processes — the arithmetic gives a single-digit percentage improvement in cut, not a qualitative win. It is worth doing because it is cheap and because a good starting assignment is what the balancer's reluctance then preserves, not because it will move the headline number on its own. Say so, so that a measured ~8% is not read as a failure.
The honest risk. pic2d may be the wrong benchmark to prove this on. It is already load-balanced, so the best available assignment is close to the initial one and a balancer that does nothing scores nearly perfectly. That makes it a good regression test — it must not get slower — but a poor demonstration that comm-aware placement helps. A workload with genuine imbalance and real neighbour communication is needed to show the term earning its keep, otherwise "did not make things worse" is all that can be claimed.

Open questions

  • Does the comm graph capture the GPU-direct path at all? Step 2 exists to answer this. The send goes through CkArray::sendToPe like any other array message, so it should — but that is read from code, not yet observed on a run.
  • LDCommData::bytes is an int. At 5.9 MB per message that is roughly 360 messages per edge before it wraps. The narrow LBTurnInstrumentOn/Off window keeps this safe today; widening the field is an ABI change across every LB and every stats message.
  • Group and nodegroup device sends bypass CkArray::sendToPe, so their payload size is discarded rather than recorded. Harmless while only array elements form object-to-object edges, but it is why the take-and-clear on the array path must stay unconditional.
  • Overlap between communication and computation is not modelled — the objective adds them. This is the same question Phase 2 asks about CPU/GPU overlap, and probably wants the same answer.
  • A GPU group is a (physical node, device) pair, not a process. The two-level decomposition silently assumes exactly one process per device; the identity breaks otherwise. Add an assertion in the group-building loop — if any group's peIds span more than one CmiNodeOf value, log it and fall back — rather than leaving the precondition implicit.
  • CMK_CUDA is defined to 0 in non-CUDA builds (conv-config.h:123), not left undefined, so both balancers' #ifndef CMK_CUDA branches are dead in every build. Normalise every guard to #if CMK_CUDA before adding more of them.

Where the design claims come from

This plan was revised against the published literature on communication-aware load balancing and against the sources in this tree. Two different standards of evidence apply, and they are kept separate deliberately.

In-tree claims — the ObjGraph defects, the tier predicate, ScotchTopoLB's torus, the LBTurnCommOn convention, the vertex-load floor, pic2d's periodic 8-neighbour stencil, the CMK_CUDA guard — were each read out of the sources and are cited inline by file and line. They are checkable and should be checked when touched.

Literature-derived claims drove the following revisions: the bottleneck objective form (sum per PE, then max), send/receive as a max rather than a sum, the two-constant α/β tier model, the epoch multiplier relating per-iteration communication to one-time migration, deriving rather than sweeping the weight, restricting candidate destinations to the communication neighbourhood, the non-monotonicity argument against a comm-based sort key, the Graham bounds on ordering, the balance-as-constraint alternative, concurrent rather than pairwise calibration, and the migration-cost-as-bottleneck-metric change in GPU_LB_PLAN.html Phase 3.
