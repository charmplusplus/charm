Communication-Aware GPU Placement

Should we build a new comm-aware load balancer or reuse one — and what should it actually do? Companion to GPU_LB_PLAN.html, Phase 6.

The problem this has to solve

On Delta, GreedyRefineCentralGPULB moved 32 of 64 pic2d chares and made the application ~52% slower — ~20 ms/iteration against 13.4 ms with migration disabled — and it stayed slower long after migration had finished. The lasting cost is therefore the assignment, not the move. The balancer traded a marginal compute gain (objGPU is about 0.1% of step time) for a ghost-exchange pattern that now crosses process and device boundaries, and nothing in its objective could see that it had done so.

Migration cost is not communication cost. The two are easy to conflate and often discussed together, but they behave completely differently. Migration cost is paid once, at the load-balancing step. Communication cost is paid every iteration, forever after. A migration-cost term can only make the balancer reluctant, and reluctance is indiscriminate: it penalises a move that improves locality exactly as much as one that destroys it. At best it preserves whatever locality the initial mapping happened to have — it can never create any. Because the pic2d regression persists in steady state, reluctance alone cannot fix it.

Why none of them can be adopted as-is

1. A partitioner's output is an arbitrary relabelling

METIS, Scotch and recursive bipartitioning all solve "cut this graph into k balanced parts." Nothing in that formulation says part 3 should be the part that already lives on PE 3. Run at every LB step, a partitioner therefore remaps nearly everything — which is precisely the failure mode we are trying to fix. Mitigations exist (seeding from the current assignment, matching parts to PEs by maximum overlap) but they are bolt-ons to a formulation that has no notion of an incumbent placement.

2. They are flat over PEs; our problem is two-level

The GPU decision (which device, therefore which process) and the CPU decision (which PE inside that process) have different cost structures and different balance targets. A flat partitioner sees N interchangeable parts. On a 4-GPU node with 8 PEs per GPU, "PE 7 and PE 8" is a device boundary while "PE 6 and PE 7" is not, and a flat model cannot express that.

3. Edge weights are transport-blind

In every one of these, a cut edge costs the same wherever it lands. On a multi-GPU node the same logical edge spans four cost tiers that differ by orders of magnitude — a same-device exchange versus a cross-node RDMA staged transfer. findTransferModeDevice already classifies exactly this for any (src, dst) pair, and none of the existing balancers consult it. ScotchTopoLB is the only one whose model could express it, and it is not in the build.

4. Single load dimension, and it is the wrong one

ObjGraph sets CkVertex::compLoad = objData[v].wallTime — host CPU time only. The SM-normalised gpuTime that this whole branch exists to collect never reaches the graph. METIS multi-constraint partitioning (ncon = 2) could carry CPU and GPU as separate balance constraints, which is a genuinely good fit, but objections 1–3 still stand.

Verdict: extend GreedyRefineCentralGPULB; reuse ObjGraph, not a balancer. The refinement structure — an incumbent assignment, a per-object decision to stay or move, a tolerance governing how much improvement justifies a move — is the right shape for this problem and is exactly what the partitioners lack. What we are missing is a term in the objective, not a different algorithm. ObjGraph (src/ck-ldb/ckgraph.h) already does the tedious half: it converts LDStats::commData into per-vertex sendToList/recvFromList with message and byte counts, resolves object keys through the comm hash, handles multicast, and writes decisions back via convertDecisions. Reuse it for plumbing and keep our own placement logic.

Worth borrowing rather than adopting

  • RecBipartLB's RefineBoundary — a KL/FM gain-based boundary swap. Once a comm term exists, this is the natural inner refinement pass: it only considers objects on a partition boundary, which is where locality is actually won or lost, and it is cheap.
  • METIS as a startup mapper, not a balancer — see below.

The one place a partitioner genuinely fits

Objection 1 — that a partitioner remaps everything — costs nothing when nothing has been placed yet. At t = 0 an arbitrary relabelling is free.

pic2d currently builds its array with a bare CProxy_Patch::ckNew(n_chares_x, n_chares_y), so it gets DefaultArrayMap: a linearisation of the 2D index space blocked over PEs. For a 5-point stencil that is a reasonable but not good mapping — it gives long thin strips with a large surface-to-volume ratio rather than compact blocks.

So the division of labour is:

  • Startup: a partitioner (or, for a structured stencil, simply a 2D blocked CkArrayMap — cheaper and near-optimal) produces a communication-minimising initial mapping.
  • Every LB step after that: GreedyRefineCentralGPULB with a comm term maintains it, moving objects only when the load imbalance is worth the locality it breaks.

Neither half works alone. A good initial map with a locality-blind balancer is destroyed at the first AtSync — which is the regression we measured. A locality-aware balancer starting from a bad map spends every step climbing out of a hole it should never have been in.

What the balancer should do

The cost table

One table, shared with Phase 3's migration cost. Tiers, not hard-coded numbers — the numbers are calibrated (see below).

TierConditionMechanismRelative cost
T0Same PENone — no message at all0
T1Same process, same GPUDevice pointer handoffNear 0
T2Same process, different GPUPeer D2D copybytes / peer BW
T3Same node, different processCUDA IPCbytes / IPC BW + handle overhead
T4Different nodeHost-staged RDMA2 × bytes / host BW + staging

The tier for any (srcPe, dstPe) pair is what findTransferModeDevice already returns, refined by gpu_device_id equality to split T1 from T2.

The objective

Per-iteration cost of a candidate assignment, as seen by the busiest resource:

cost(assignment) = max( maxGpuGroupLoad,        // existing, Phase 1
                        maxPeCpuLoad )           // existing, Phase 1
                 + commWeight * maxPeCommTime    // new

// Communication charged to the PE that pays it, not summed globally --
// a hot spot on one PE stalls the step even if total traffic is low.
maxPeCommTime = max over pe of ( sum over edges (o, nbr) with place(o) == pe
                                   of tierCost(pe, place(nbr)) * bytes(o, nbr) )

Charging communication to the busiest PE rather than summing it globally matters: total edge cut is what a partitioner minimises, but what lengthens a step is one PE's inbox, and those are different quantities whenever the cut is unevenly distributed.

Scoring a candidate placement

double commCost(int objIdx, int candidatePe) {
  double c = 0;
  for (const CkEdge &e : vertices[objIdx].sendToList) {
    int nbrPe = (newPe[e.getNeighborId()] >= 0)   // placed already this pass?
                  ? newPe[e.getNeighborId()]      //   use the new decision
                  : oldPe[e.getNeighborId()];     //   else assume it stays put
    c += tierCost(candidatePe, nbrPe) * e.getNumBytes();
  }
  // recvFromList likewise; an edge is charged once to each endpoint's PE
  return c;
}
Ordering hazard. A comm term inside a greedy loop is order-dependent: when object i is placed, some of its neighbours are not placed yet. Scoring against the peer's old PE when it has not yet been placed is the standard treatment in a refinement balancer, and it is a good prior here precisely because most objects will not move. Two refinements if it proves insufficient: run a second scoring pass once all placements are known (cheap — the assignment loop is not the bottleneck), or process objects in graph order (BFS from a seed) rather than load order, so neighbours are usually already placed. The second interacts badly with the descending-load ordering that greedy packing needs, so prefer the second pass.

Calibrating the constants

Three options, in increasing order of fidelity and effort:

  1. Hard-code per architecture. Fragile, but a starting point. PCIe 4.0 measured at roughly 25 GB/s on Delta's A40s.
  2. Micro-benchmark at startup. One D2D copy per tier on the first LB step. The IPC handle-open cost measured here also feeds the deferred A-vs-C staged-versus-IPC switching decision.
  3. Learn from history. Record (bytes, tier, elapsed) for each actual transfer and fit. Most accurate, most machinery; defer.

Start with (2) — it is a few dozen lines and removes the per-machine fragility of (1).

commWeight

The objective adds seconds of compute to seconds of communication, so in principle commWeight is 1 and the terms are directly comparable. In practice it should be exposed as a tunable, because the two are measured very differently: compute load comes from CUPTI and the LB timers, communication is estimated from a byte count and a bandwidth constant, with no account of overlap between communication and computation. Making it a parameter also lets it join the existing concurrent (A, B) search as a third dimension, so the best value is picked by measurement rather than argued about.

Step 5 is the one that is easy to get wrong. Phase 1 already taught this lesson once: a term that influences per-move decisions but is absent from the reported max_load is invisible to receiveSolutions, which then falls through to its fewest-migrations tie-break. The same trap applies to the sort key — if placement is scored on communication, the ordering should reflect it too (heaviest-communicating objects placed first, when they still have a free choice of PE).

Validation

Each step is measurable on its own; do not stack them before measuring.

  • Step 2, single GPU: edge dump matches the known 5-point stencil. This catches a broken graph before any placement logic depends on it.
  • Step 7 alone, no LB: blocked map versus DefaultArrayMap, migration disabled. Isolates the initial-mapping gain from everything else.
  • Steps 3–5, 4 processes × 8 PEs on Delta: the headline number is iteration time with the balancer against the 13.4 ms no-migration baseline. Migration count should fall well below 32/64, but count is a diagnostic — time is the result.
  • Regression: a genuinely imbalanced run must still migrate. A comm term that simply freezes everything in place is not a fix, and would look identical to success on pic2d, which is already balanced.
The honest risk. pic2d may be the wrong benchmark to prove this on. It is already load-balanced, so the best available assignment is close to the initial one and a balancer that does nothing scores nearly perfectly. That makes it a good regression test — it must not get slower — but a poor demonstration that comm-aware placement helps. A workload with genuine imbalance and real neighbour communication is needed to show the term earning its keep, otherwise "did not make things worse" is all that can be claimed.

Open questions

  • Does the comm graph capture the GPU-direct path at all? Step 2 exists to answer this. The send goes through CkArray::sendToPe like any other array message, so it should — but that is read from code, not yet observed on a run.
  • LDCommData::bytes is an int. At 5.9 MB per message that is roughly 360 messages per edge before it wraps. The narrow LBTurnInstrumentOn/Off window keeps this safe today; widening the field is an ABI change across every LB and every stats message.
  • Group and nodegroup device sends bypass CkArray::sendToPe, so their payload size is discarded rather than recorded. Harmless while only array elements form object-to-object edges, but it is why the take-and-clear on the array path must stay unconditional.
  • Overlap between communication and computation is not modelled — the objective adds them. This is the same question Phase 2 asks about CPU/GPU overlap, and probably wants the same answer.
