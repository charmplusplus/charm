LeanMD GPU Port

Porting LeanMD to GPUs as a benchmark for METIS-then-diffusion load balancing. Parked — DiffusionLB porting comes first. Companion to DIFFUSION_GPU_LB_PLAN.html.

Status, 2026-08-20. Not started, and deliberately not next. The agreed order is: port DiffusionLB from origin/diffusionlb onto cupti_lb_reconverse first (Phase A of DIFFUSION_GPU_LB_PLAN.html), because that work is independent of which benchmark it eventually runs on. This document exists so the LeanMD investigation is not repeated from scratch later. Everything below was read out of the source at /home/aditya/LeanMD (cloned from github.com/UIUC-PPL/LeanMD) and is cited by file and line.

One thing already landed from this investigation: the n_migrateobjs loop-bound bug in GreedyRefineCentralGPULB::fillData, described under "Already fixed" below. LeanMD is what exposed it; the fix is in and compiles.

Why LeanMD is a candidate at all

pic2d failed as a benchmark for GPU-aware load balancing for reasons now measured rather than assumed: 24 host round trips per iteration (21 of them a Jacobi halo-exchange loop moving 43 KB), kernels too narrow to occupy the SMs, and an elasticity of GPU work to step time of about 0.3. LeanMD offers four things pic2d does not.

  • A correctness oracle. Main::run compares initial against final total energy against ENERGY_VAR = 1e-5 and prints pass/fail. That catches migration corrupting state — the failure mode we currently have no automatic detector for. pic2d has nothing equivalent.
  • A locality-blind starting point. See "What METIS actually fixes" below. The default Compute placement is round-robin, so a startup partitioner has a large, structural gain available rather than the single-digit percent projected for pic2d.
  • Mixed migratability, which exercises code paths no current benchmark reaches.
  • Real physics with real lineage — Lennard-Jones MD, the mini-app for NAMD, which is the application the Charm++ load-balancing literature is built on.

The object model

Two arrays with completely different economics. This asymmetry is the whole reason LeanMD is interesting, and the reason it is awkward.

Count (3×3×3)MigratableState carriedLoadComm degree

Compute (6D array)1026Yes~100 bytes: SDAG state, stepCount, two CkSectionInfo, energy[2] (Compute.cc:63-74)all the force work2 Cells

Computes per cell is NUM_NEIGHBORS/2 + 1 = 38 with the default KAWAY 2,2,1 (NBRS 5×5×3 = 75). The comm graph is bipartite and every Compute has degree 2. That single fact drives the rest of this document: a Compute's ideal home is wherever its two Cells live, and it costs nearly nothing to put it there.

How LB works when the load-bearing objects hold no data

Migrating a Compute moves ~100 bytes. What it actually relocates is (a) where the O(NA·NB) force computation runs, and (b) where the position multicasts and force reductions flow. This is the NAMD model — patches pinned, stateless computes free to move — and it means placement is the entire decision. A Compute for pair (A,B) sitting on A's PE needs one remote position stream and one remote reduction; on a third PE it needs four. Same load, double the traffic.

What METIS actually fixes

The strongest argument for this benchmark. Cell.cc:69:

int currPe = CkMyPe();
...
computeArray[index].insert((++currPe) % CkNumPes());

Round-robin. All 1026 force computations are placed with no reference to where their Cells live, so both position multicasts and both force reductions are remote essentially always. Unlike pic2d — where DefaultArrayMap already yields a reasonable blocked layout and the projected startup-mapping gain was single digits — here the baseline is effectively random, and a communication-minimising partition at the first LB step has a large structural inefficiency to remove.

Why diffusion then works without modification

MetricComm::popBestObject(nbor) (DiffusionMetric.C:161-195) selects, among objects fitting the neighbour's capacity, the one maximising externalComm[nbor][i] — whichever object already communicates most with the destination node.

A Compute's entire communication is with its two Cells. So "the object that talks most to node N" is exactly "a Compute whose cells are on node N." The diffusion metric reproduces the NAMD placement heuristic with no LeanMD-specific code. Combined with ~100-byte transfers, diffusion can shed load aggressively with no migration-cost term fighting it.

The risk that decides whether this is worth doing

Kernel granularity — resolve this before writing any code. A Compute evaluates one cell-pair interaction. At the stock 100–250 atoms per cell (PARTICLES_PER_CELL_START/END, defs.h) that is 104–6×104 pair evaluations — a tiny, narrow kernel. Launching 1026 of them per step reproduces pic2d's exact pathology in new clothing: not kernels that are too short, but kernels too narrow to occupy the SMs, which is what drove SM-normalised GPU load toward zero and elasticity to 0.3.

Two ways out, and one must be chosen up front:

  • Much larger cells — raise PARTICLES_PER_CELL_* into the thousands and widen PTP_CUT_OFF/CELL_SIZE to match. Fewer, fatter Computes. Costs LB granularity (fewer objects to balance).
  • Batch many Computes into one launch — keeps LB granularity fine, but means a PE's resident Computes are co-scheduled, which complicates attributing gpuTime back to individual objects. CUPTI attribution is per-kernel, so batched objects would need their share estimated by pair count rather than measured.

The second preserves what makes LeanMD a good LB benchmark but weakens the per-object GPU load measurement this whole branch exists to collect. The first is simpler and is the recommended starting point.

Decisions to make before porting

1. Do Cells become migratable?

Stock LeanMD pins them, which makes this a pure communication-objective benchmark: migration cost is ~0 everywhere, so nothing exercises gpuPupSize, the export-and-pull path, the T1–T4 migration tiers, or the GPU memory constraint. Those are Phases 3, 4, G and H of the other two plans.

Recommendation: make Cells migratable. One line plus a PUP routine for the atom vector. It turns LeanMD into a full-stack test — Cells carry MB-scale device-resident atom arrays whose size correlates with load, which is the honest dilemma (the most valuable objects to move are the most expensive to move) and the only way the memory-capacity machinery gets tested.

2. METIS cannot express pinned vertices

If Cells stay pinned, plain MetisLB is wrong for the startup step: METIS 5.x PartGraphKway has no fixed-vertex support, so it would assign new PEs to all 27 Cells and convertDecisions would write migration targets for non-migratable objects. Either make Cells migratable (decision 1, which dissolves the problem) or use Scotch, which does support fixed vertices, as the startup partitioner.

3. Where GPU load lives

GPU-ifying calcPairForces/calcInternalForces (physics.h) puts gpuTime on Computes — the cheap-to-migrate array. That is the favourable arrangement: the balanced dimension sits on the objects that move nearly free. Under one process per device, diffusion's node-level equalisation is GPU-group equalisation directly.

Gotchas checklist

  1. The getVertexLoad() 0.1 s floor (ckgraph.h:152) flattens every vertex weight at this granularity — a Compute handling 100–250 atoms per side is orders of magnitude below it. METIS would partition with uniform weights: pure edge cut, no balance constraint. Survivable for a startup mapper, but not what the code appears to do. Same issue applies to DiffusionCore.C:101.
  2. Section proxies must survive migration. Cells reach Computes through multicast sections built in Cell::createSection(); Compute::pup carries mcast1/mcast2 and resets set_redNo(0) on restart. Diffusion migrating Computes every LB step will exercise section rebuild far harder than LeanMD's stock RefineLB runs ever did.
  3. Load evolution is weak as shipped. Initial imbalance is a static linear ramp — myNumParts = START + (myid*(END-START))/nCells, Cell.cc:10 — and atoms start on a lattice with ±0.1·MAX_VELOCITY jitter, a cold near-uniform system. Atoms redistribute only every MIGRATE_STEPCOUNT = 20 steps. Genuine evolving load needs a driver: shock propagation through the LJ solid is the recommended mechanism (front velocity is set by the Hugoniot relations, giving an analytic check, and it proxies materials-science MD directly). Free expansion is easier but decays monotonically to uniform.
  4. Compute load is N_A × N_B, so it evolves as cell populations change — and message sizes evolve with it, since positions and forces are both proportional to atom count. Load and communication move together here, unlike a fixed-size stencil.
  5. Energy conservation doubles as a migration oracle. Wire the pass/fail check into the test loop: any migration that corrupts device-resident state should break conservation. This is the single most valuable thing LeanMD brings.

Already fixed

GreedyRefineCentralGPULB::fillData bounded its object loop by stats->n_migrateobjs while indexing stats->objData[i]. n_migrateobjs is a count of migratable objects (CentralLB.C:485 computes it with count_if over the whole array), not an upper bound on their indices — objData is filled in per-PE registration order and never partitioned. The tail of objData was therefore neither balanced nor charged as background load; its load vanished from the objective entirely.

Latent whenever every chare is migratable, which is why pic2d and jacobi2d never exposed it. LeanMD would trigger it immediately: 27 pinned Cells + 1026 migratable Computes gives objData.size() = 1053 against n_migrateobjs = 1026, dropping 27 objects. Fixed by bounding the loop with objData.size() and sizing the GObj vector to match; totalObjs stays the migratable count because it bounds migrationsAllowed. This also corrects the mean_oload denominator, previously wrong whenever a non-migratable object sat in the prefix. Compiles clean.

The same pattern exists in GreedyRefineCentralLB.C (lines 265 and 443) and was left alone — same two-line fix if that balancer is ever used on a mixed-migratability workload.

L2's gate is the one that matters. The elasticity test — E = Δlog(step time)/Δlog(GPU work), measured by scaling the problem and requiring E ≥ 0.8 — is what pic2d fails at 0.3. A benchmark that fails it is measuring its latency chain, and any load-balancing result taken on it is noise. If LeanMD cannot pass L2 under either granularity option, it is not worth carrying further and the effort should go to a purpose-built proxy instead.

Status: L0–L2 complete

The port lives in examples/charm++/cuda/gpudirect/leanmd/ (commit 404ee32d3).

L2 passes its gate. Scaling particles per cell from 500 to 1000 raises pair work 4× (the kernel evaluates NA×NB pairs regardless of the cutoff test) and raises mean step time from 94.20 ms to 332.56 ms — a 3.53× ratio, so E = 0.91. Measured on an RTX 3050 laptop at 3×3×3 cells, +p4. pic2d sits at 0.3 on the same test. LeanMD is device bound and is worth carrying to L3.

Correctness. Validated against the unmodified CPU benchmark rebuilt at matching granularity: initial and final energies agree to all ten printed digits, at +p1, +p2 and +p4, over 60 steps — which spans two migration rounds, so the device binning and exchange are covered too, not just the force kernel.

What device residency cost, structurally

Two pieces of the original could not survive the constraint, and both were load-bearing.

The CkMulticast section is gone in both directions. It carried positions down as a multicast and forces back up as a CkReduction::sum_double. Charm++ reductions combine host buffers, so keeping the upward half would have meant a D2H on every Compute and an H2D on every Cell, every step — the exact traffic the port exists to remove. Positions now go out as point-to-point nocopydevice sends and forces return the same way, folded in by a kernel. Each message carries the ordinal its Cell handed out, so a returning array lands in its own slot; that is what the CkSectionInfo cookie used to do, and a Compute now recovers its two cells from its own 6D index instead. Two consequences: the spanning tree is lost (27 unicasts per Cell per step, since no device-buffer multicast exists), and forces sum in arrival order rather than tree order, so totals are no longer bit-identical run to run.

Particle migration moved to the device. The host-side sort in migrateParticles would have pulled the entire particle array back every 20 steps. A single kernel now classifies, wraps and compacts; stayers are adopted by a pointer swap and outgoing buckets ship as device buffers. Only the per-bucket counts reach the host.

Bugs found on the way

  • Non-reproducible initial conditions, pre-existing. Initial velocities came from srand48/drand48, which share one global state. Every PE of an SMP build is a thread of one process, so Cell constructors on different PEs corrupted each other's sequence: initial energy differed on every run at +p4 and varied with PE count. Confirmed by reproducing it in the untouched CPU benchmark. This would have made every A/B comparison between balancers meaningless — the two runs would not have been simulating the same system. Fixed with erand48, seeded to reproduce what a single-PE stock run produced.
  • Two timesteps, not one. updateProperties advances velocity by DEFAULT_DELTA × 10-20 and position by plain DEFAULT_DELTA, because acceleration is in m/s² and velocity in Å/fs. A single dt in the integration kernel rescales the dynamics by 1020.
  • Kinetic and potential energy were in different units. updateProperties scales kinetic energy by 1010 to reach the milliJoules the pair potential is already in. Omitting it makes the conservation test compare unlike quantities.
  • Positions, not Particles, on the wire. The kernels read only pos; sending full Particle structs would have put 80 bytes per atom on the wire where the original put 24, tripling communication volume in a benchmark built to exercise a communication-aware balancer.
  • An unreachable indexing bug in the original. migrateToCell can return offsets of ±2, which would index past the end of its 27-entry vector. It cannot fire at these parameters (an atom drifts at most 2 Å between migrations, against a 30 Å cell), but the device version clamps rather than inheriting a latent memory stomp.

Still open before L3

Cells remain setMigratable(false) — which is exactly L3. Their pup currently packs a host particle vector that is empty after initialisation, so making Cells migratable means pulling the array down from the device on pack and pushing it back on unpack, or routing it through the device-migration path the branch already has. Computes migrate today and are exercised by the +balancer run; their device scratch holds nothing that outlives a step, so it is released by the destructor and reallocated lazily on the new PE.
