GPU Migration Data Paths

When a chare migrates, its host state is packed and sent — but its device buffers have to physically move between GPUs. There are five ways to do that. They differ by a factor of three in copies and a factor of four in peak device memory, and each one optimizes a different scarce resource.

What a migration actually moves

A migrating chare has two kinds of state. The host side is serialized by its PUP routine into a normal Charm message. The device side — call it S bytes across k buffers — has to get from the source GPU into freshly allocated buffers on the destination GPU.

Every design below is a different answer to one question: how many times do those S bytes get copied, and how much memory is live at once while it happens. The transport used for each hop (direct memcpy, CUDA IPC, RDMA) is a separate axis, decided by where source and destination sit relative to each other.

Why memory leads

Staging buffers come from a device region reserved at startup via +gpulbbuffer. That reservation is unavailable to the application for the whole run, whether or not anything migrates — and when a load-balance step migrates many chares at once, demand is N·S per side. Exceeding it is not graceful: it aborts with "Not enough memory on device Load balance buffer". On a 4 GB card running pic2d, chare state alone is ~800 MB. Copies cost microseconds; memory costs the run.

Optimizes

Simplicity and lifetime safety. The source owns nothing after packing, so there is no deferred destruction, no acknowledgement protocol, and no window where a destination reads memory the source might free. That is a real asset — it is why this is the version that works.

Costs

The most copies and the most memory of any option, plus a full cudaDeviceSynchronize() on the migration path that stalls the whole device, not just the stream. When many chares migrate together those syncs serialize.

B · Export handles, destination pulls

Ported, unreachable No cross-node path

Optimizes

Source-side memory. Removing source staging halves that side's LB-buffer requirement, which is the reservation you can then give back to the application.

Costs

cudaIpcOpenMemHandle runs roughly 100 µs–1 ms and is paid per buffer, per migration. Against ~1 TB/s device bandwidth, the one copy it saves only pays for itself somewhere around 100 MB per buffer — so a chare with several small buffers pays k times over and saves proportionally less. It also introduces deferred destruction and an ack protocol, and IPC handles must name allocation bases: pointers suballocated from the buddy allocator would silently resolve to the wrong offset. Cross-node needs CmiSendDevice, which does not exist under reconverse.

C · Host first, pull into place

Proposed Memory floor

Process the host message before the device transfer, so PUP allocates the destination chare's real buffers first. Then pull each source buffer directly into its final destination buffer. No staging exists on either side.

Optimizes

Memory, to the theoretical minimum — the bytes exist once on each side and nowhere else. +gpulbbuffer could shrink toward zero for the migration path, returning that reservation to the application permanently. It also happens to be the fewest copies, and it sidesteps the IPC base-pointer hazard because the destination pulls into freshly allocated chare buffers rather than a suballocated region.

Costs

Ordering becomes mandatory. Today whichever of the host message or the device transfer arrives second drives the unpack; this design requires host-then-device, and PUP has to split into allocate-then-fill rather than copying out of a contiguous blob. That is the real work — a rendezvous change plus a PUP restructuring, not a port.

D · Pointer handoff, same process and GPU

Implemented Unverified

Everything, within a narrow scope. This is strictly the best option wherever it applies, and it is the case that matters most for the intra-group CPU rebalancing a two-level GPU load balancer leans on.

Costs

Applicability only. It bypasses PUP entirely, so any semantics a chare's PUP routine performs beyond copying bytes are skipped — worth auditing per application.

Gap — not implemented

Transport availability under reconverse

Staging strategy and transport are independent choices, but not every transport exists here. Regular entry methods with device parameters already exercise all three working transports — the migration path can use exactly the same ones.

Source → destination Transport Used by entry methods Available to migration
Same logical node direct device-to-device copy yesyes
Same physical node pre-shared comm buffer + IPC events yesyes
Across physical nodes CmiNcpyBuffer::rdmaGet (LCI) yesyes
Across physical nodes CmiSendDevice / LRTS nono — absent under reconverse

The last row is the one that constrains the port. CmiSendDevice is charm-layer code, but RECONVERSE=1 replaces the entire converse target, and its implementation bottoms out in LrtsSendDevice from charm's ucx/mpi machine layers — also replaced. Any cross-node strategy has to be written against rdmaGet instead, which is a better fit regardless: it is already a destination-pull primitive, which is the semantics approaches B and C want.

What to pick, by topology

Case Recommendation Rationale
Same process, same GPU D · pointer handoff Zero cost. Already implemented; needs verification.
Same process, other GPU E · peer copy One copy, no handles. Currently an unnecessary gap.
Same node, other process A today → C when ready B's per-buffer handle cost likely exceeds the copy it saves.
Across nodes A today → C via rdmaGet Biggest memory win; transport already exists and pulls.

Before committing

  • Migration of GPU-resident chares currently fails on this branch under a forced-migration LB — the existing path crashes inside immigrateGPU, and the pointer-handoff path loses data. There is no known-good baseline to measure against yet, and that should be fixed before layering more on top.
  • Measure cudaIpcOpenMemHandle on the target hardware. That single number decides whether approach B belongs in the tree at all, and it is a ten-line benchmark.
  • Characterize k and S for real chares. Per-buffer handle costs scale with k; copy savings scale with S. pic2d sits near 50 MB per patch across two dominant buffers.
  • Compare reserved +gpulbbuffer against peak concurrent demand. If the reservation is sized for N·S and approach C drops it to zero, that memory returns to the application for the entire run — likely the largest single win available here.
Figures are per migrating chare: S = its device bytes, k = its device buffer count. Copy counts include the transport hop. Peak memory counts live chare buffers plus staging on each side, and doubles when source and destination share one GPU.
