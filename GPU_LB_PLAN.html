GreedyRefineCentralGPULB — Implementation Plan

Cost-aware, overlap-aware, topology-aware GPU load balancing for Charm++

Context

The current GreedyRefineCentralGPULB balances at two levels: GPU load across GPU groups (processes), CPU load across PEs within a group. It inherits the concurrent multi-parameter search from GreedyRefineCentralLB.

Known bugs and gaps:

  • Single GPU → 0 migrations: the objective reports only GPU-group load (constant with one group), so all solutions look identical and the lowest-migration solution (0) wins. Fixed in Phase 1.
  • No overlap model: max(gpu, cpu) assumes perfect overlap; gpu + cpu assumes none. Reality is somewhere between.
  • Flat migration cost: pointer handoff (free) and cross-node staging (expensive) are treated identically.
  • No GPU memory constraint: the LB can assign more objects to a GPU than its memory can hold.
  • No notion of communication locality: neighbor placement is invisible to the objective, so a move that halves an object's compute but scatters its ghost exchanges across processes scores as a pure win.
Where this stands as of 2026-08-17. The full pipeline runs end to end on NCSA Delta — 4 processes × 8 PEs on 4 A40s, 4 GPU groups, cross-process IPC chare migration, all 64 chares resuming, run completing. Phase 1 landed and the balancer now migrates. But it migrates badly: pic2d runs at roughly 20 ms/iteration with the balancer against 13.4 ms with migration disabled, and stays slower well after migration finishes. Two causes, both in this document: objGPU is about 0.1% of step time, so the balancer optimizes a negligible dimension; and neither migration cost nor communication locality appears in the objective, so it moved 32 of 64 chares for a marginal gain. Phase 3 is the direct answer, which is why the implementation order below changed.

Phased Implementation

Each phase is independently valuable and testable. Later phases build on earlier ones but don't require them.

Phase 1 — Fix the 0-Migrations Bug donecpugpu

Problem: maxLoad (the Solution objective) tracks only max(GPU group loads). With one GPU group this is constant across all solutions.

Fix: Track max PE CPU load alongside max GPU-group load during the assignment loop. Report max(maxGpuGroupLoad, maxPeCpuLoad) as the Solution's max_load. The greedy-refine target M stays GPU-only (it governs outer group-level decisions).

// After assigning each object:
g.load += obj_gpu;
p->cpuLoad += obj_cpu / p->speed;
if (g.load > maxGpuLoad) maxGpuLoad = g.load;
if (p->cpuLoad > maxCpuLoad) maxCpuLoad = p->cpuLoad;

// Reported objective:
maxLoad = std::max(maxGpuLoad, maxCpuLoad);

Effect: With one GPU, GPU-group load is constant but CPU balance varies across solutions → the best CPU balance wins → non-zero migrations. Multi-GPU also improves: a solution with good GPU balance but terrible CPU imbalance now scores worse.

Test: Single GPU + RandCentLB → verify non-zero migrations. Check that per-PE CPU imbalance improves.

Done — commit 8166caea0, plus one thing the plan missed. The objective fix alone still produced zero migrations. Greedy packing only works if objects are visited in descending order of the quantity being balanced, and ObjLoadGreater still sorted by GPU load alone — so with a negligible objGPU the order was effectively arbitrary and the CPU-aware objective had nothing to work with. The sort key in GreedyRefineCentralGPULB.h now uses std::max(load, cpuLoad) under CMK_CUDA, matching the objective. Lesson worth keeping: when changing what a greedy balancer optimizes, change its sort key in the same edit.
Phase 2 — Overlap-Aware Objective cpugpu

Problem: max(gpu, cpu) assumes the CPU and GPU timelines overlap perfectly. If the application serializes (launch → sync → compute), the actual step time is closer to gpu + cpu.

Approach: Measure the overlap coefficient α from the existing per-PE statistics, once per LB step:

// Per GPU group g:
double gpu_time = g.load;                   // aggregate GPU load
double max_cpu  = max(p.cpuLoad) for p in g // max PE CPU load in group
double measured = max(p.total_walltime) for p in g  // actual step time

// Solve for α:  measured = α·(gpu + cpu) + (1−α)·max(gpu, cpu)
// α = 0 → perfect overlap, α = 1 → fully serial
double overlap = max(gpu_time, max_cpu);
double serial  = gpu_time + max_cpu;
if (serial > overlap)
    α = (measured - overlap) / (serial - overlap);
else
    α = 0;

// Predicted step time for a candidate assignment:
predicted = α * (gpu + cpu) + (1 - α) * max(gpu, cpu);

Key insight: total_walltime in ProcStats already measures the actual step duration — LBMachineUtil accumulates CkWallTimer() between StatsOn()/StatsOff(), which bracket the LB step. No new instrumentation needed — just compare predicted vs measured to calibrate α.

Caveat: α is group-level, not per-object. An object that does cudaDeviceSynchronize() contributes serial coupling, but we can't attribute that to individual objects from the aggregate. α is a best-effort approximation.

Fallback: If total_walltime isn't reliable (first LB step, or tracing disabled), default to α = 0 (Phase 1 behavior).

Phase 3 — Migration-Cost-Aware Decisions topo

Problem: The B tolerance parameter (migration reluctance) is topology-blind. A pointer handoff within the same GPU group is free; a cross-node staged migration is expensive. The LB treats them identically.

Transport modes and costs:

ModeConditionData costFixed overhead
Pointer handoffSame process, same GPU0~0
MemcpyStrategySame process, cross GPU∝ gpu_size (peer D2D)~0
IpcStrategyCross process, same node∝ gpu_size (IPC D2D)synchronous pull wait, 25–240 μs measured
Staged pathCross node2× gpu_size (stage + ship)cudaDeviceSync + alloc

Design: Replace the flat B tolerance with a per-move cost model. For each candidate (object, destination PE) pair:

// Migration cost in seconds (estimated)
double migCost(int objIdx, int srcPe, int dstPe, size_t gpuBytes) {
    if (CmiNodeOf(srcPe) == CmiNodeOf(dstPe)) {
        if (sameGpuGroup(srcPe, dstPe))
            return 0;                         // pointer handoff
        return gpuBytes / PEER_BW;            // ~600 GB/s PCIe / NVLink
    }
    if (CmiPeOnSamePhysicalNode(srcPe, dstPe))
        return IPC_OPEN_COST + gpuBytes / IPC_BW;
    return STAGE_COST + 2 * gpuBytes / HOST_BW;
}

// Only migrate if benefit exceeds cost:
double benefit = loadReduction(obj, srcPe, dstPe);
if (benefit > migCost(...) * costWeight)
    migrate;

Bandwidth constants can be measured once at startup (a small D2D benchmark) or hard-coded per architecture.

Measured on Delta (4× A40, 2026-08-17), superseding the estimates above. The dominant fixed cost for a cross-process move is not the IPC handle open — it is the synchronous pull wait, because migration completion now blocks rather than finishing from a CUDA callback. Peer copies run over PCIe at roughly 25 GB/s, and observed chare payloads were 590 KB–5.9 MB, giving 25–240 μs per migrated chare. Use that as IPC_FIXED_COST until the async path lands (see ASYNC_MIGRATION_PLAN.md), at which point this term shrinks toward the pure bandwidth cost.
Why this phase is now the priority. On Delta, with the balancer migrating, pic2d ran at ~20 ms/iter against 13.4 ms with migration disabled — about 52% slower, and it stayed slower long after the migration finished, so this is the chosen assignment being worse rather than migration overhead. The balancer moved 32 of 64 chares for a marginal compute gain because every move looks free to it. A migration cost model is what lets it decline. Pair this with a communication-minimizing initial mapping: a good starting assignment plus a reason to stay put is the combination that fixes the regression.
Prerequisite already met: per-object sizes are already in the stats. LDObjData::gpuPupSize gives the migration payload for the data-cost term, and the _lb_obj_index user-data slot gives the device allocation footprint. No new plumbing — read them the way GreedyRefineCentralLB::fillData already does (lines 307-308).
Phase 4 — GPU Memory Constraint (port, not new work) memgpu

Status: this branch's GreedyRefineCentralLB.C already implements exactly this, at group level (lines 477-617): per-group gpu_mem_remaining and pool_buff_mem_remaining budgets seeded from ProcStats, a veto when either end's staging buffer can't hold gpuPupSize or when the destination GPU's free memory (with a 5% headroom margin) can't hold gpuAllocSize, and budget decrements on each accepted move.

// Existing veto logic to port into GreedyRefineCentralGPULB:
if (chosen_gi != src_gi && obj->gpuPupSize > 0) {
    if (grp[src_gi].pool_buff_mem_remaining  < obj->gpuPupSize ||
        grp[chosen_gi].pool_buff_mem_remaining < obj->gpuPupSize)  → keep on src
    if ((size_t)(0.95 * grp[chosen_gi].gpu_mem_remaining) < obj->gpuAllocSize) → keep on src
}
// On accept: decrement both groups' pool budgets and dest group's gpu_mem.

Work: port this into GreedyRefineCentralGPULB's assignment loop, with two refinements: credit gpu_mem_remaining back to the source group when an object leaves it, and skip the pool_buff veto for moves the new migration paths make staging-free (pointer handoff and export-and-pull don't consume the source LB buffer — only the destination's).

Phase 5 — Topology-Aware Group Preferences topo

Problem: The outer greedy loop picks the lightest GPU group globally. On a multi-node system, migrating to a remote node's GPU group is much more expensive than a nearby one.

Design: Weight group selection by transport cost. Instead of pure lightest-first, prefer groups reachable by cheaper transport:

// Candidate scoring:
for (int gi = 0; gi < nGroups; gi++) {
    double effectiveLoad = gpuGroups[gi].load;
    double topoPenalty = migCost(obj, srcPe, gpuGroups[gi].peIds[0], obj_gpu_size);
    score[gi] = effectiveLoad + topoPenalty * topoWeight;
}
int chosen_gi = argmin(score);

This naturally prefers local GPU groups when loads are similar, falling back to remote groups only when the load imbalance justifies the migration cost.

Additional Considerations

SM Utilization Normalization

The CUPTI pipeline already normalizes GPU load by SM utilization (sweep-line over kernel intervals). This means gpuTime reflects effective GPU occupancy, not just wall-clock kernel duration. Two objects that each use 50% of SMs simultaneously have gpuTime that correctly sums to 1× step time, not 2×. This is important for the outer GPU-group objective: the aggregate gpuTime across objects in a group approximates the group's actual GPU wall time.

Non-Migratable Object Accounting

Non-migratable objects contribute to both bgload (GPU) and cpuLoad (CPU) as background load on their PE. The current code handles this correctly (lines 306-311 in fillData). The overlap model should include this background in its α calculation.

Historical Load Smoothing

A single LB step's load might be noisy (e.g., particle imbalance varies per iteration). The LB could smooth loads over K recent steps using an exponential moving average. This is especially relevant for the overlap coefficient α, which should be stable across steps rather than swinging between 0 and 1.

Concurrent Parameter Search

The current design runs up to NUM_SOLUTIONS = 225 parameter combinations across PEs concurrently (14 A-values × 16 B-values, plus pure greedy on PE 0). Each PE computes a solution with different (A, B) refine parameters and reports its objective; receiveSolutions picks the fewest-migrations solution within 1.003× of the best feasible load. All phases above are compatible with this: each PE evaluates the same cost model with different refine tolerances, and the reported objective captures both dimensions. Note the selection rule's bias toward fewer migrations is exactly what turns an undiscriminating objective into 0 moves — Phase 1's fix works because it makes the objective discriminate.

Two GPU Sizes, Two Meanings

Phases 3 and 4 need per-object GPU sizes, and both already exist with distinct roles: LDObjData::gpuPupSize is the wire size — bytes that move during a migration — and drives the migration-cost model and staging-buffer budget; the _lb_obj_index user-data slot carries the HAPI-attributed allocation size — the object's resident device footprint — and drives the GPU-memory constraint. Don't conflate them: an object can pup a small subset of a large resident allocation, or vice versa.

Relationship to GreedyRefineCentralLB on This Branch

This branch's GreedyRefineCentralLB.C was already made GPU-group-aware (group aggregation by gpu_device_id, memory budgets, size-based vetoes). GreedyRefineCentralGPULB adds the two-level CPU dimension but currently lacks the memory logic. The end state should be one LB, not two near-copies — after Phase 4 ports the memory logic across, evaluate folding the remaining differences and retiring one of the two.

Bandwidth Calibration

Phase 3's cost model uses bandwidth constants. These could be:

  • Hard-coded per architecture: PCIe 4.0 ≈ 25 GB/s, NVLink 3.0 ≈ 600 GB/s. Simple but fragile.
  • Measured at startup: Small D2D benchmark on first LB step. The IPC handle-open cost can be measured alongside, feeding the A-vs-C switching decision.
  • Measured from migration history: After each migration, record (bytes, time, mode). Refine the cost model from actual measurements.

Interaction with Existing LB Ecosystem

This LB can be composed via MetaBalancer or chained with other LBs. The two-level structure means it's a natural fit for HybridLB (GPU-aware at the node level, another strategy at the inter-node level). The cost model should be usable by other GPU-aware LBs, not locked into GreedyRefineCentralGPULB — consider factoring it into a shared utility.

Why this order changed. The original order ran the phases as numbered. After Phase 1 landed and the balancer was measured on Delta, the binding problem turned out to be that every migration looks free, not that the compute model is imprecise — so Phase 3 moves ahead of Phase 2, and Phase 5 is small enough to fold into it as the group-selection term of the same cost function. Phase 2's overlap model only matters once the balancer stops making moves that lose more to migration and lost locality than they gain in compute.

Phase 3 also pairs with work outside this document: a communication-minimizing initial mapping for pic2d, which currently uses DefaultArrayMap via a bare CProxy_Patch::ckNew(nx, ny). A good starting assignment plus a cost model that gives the balancer a reason to stay put is the combination that addresses the regression; either alone is unlikely to.
