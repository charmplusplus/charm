Metis + Diffusion GPU Balancing

One METIS partition to establish locality, then GPU-aware diffusion to maintain it. Supersedes the comm-term work in COMM_AWARE_LB_PLAN.html.

What changes, and why

COMM_AWARE_LB_PLAN.html concluded: extend GreedyRefineCentralGPULB, reuse ObjGraph, don't adopt a balancer. That verdict rested on a survey of what this tree contains — and the survey missed a branch. origin/diffusionlb exists, it is communication-aware, and its comm bookkeeping is most of what the comm term was going to be built from scratch.

It also appears to be the implementation behind the 2026 PDSEC result that reports GreedyRefine producing the best load balance and the worst communication locality of every strategy tested, with diffusion achieving a 2× improvement in maximum per-PE communication time on a PIC benchmark. Its print_external_comm / print_internal_comm entry points emit exactly the external/internal ratio that comparison used. If that is the same code, then the pic2d regression is a published property of the strategy family we inherited, and the fix is to change strategy rather than to patch a term onto the one that loses.

New architecture: partition once, diffuse thereafter. Step 0 — MetisLB produces a communication-minimising global assignment from a cold start. Every step after — DiffusionLB, made GPU-load-aware, maintains it with local, incremental, comm-aware transfers that never remap globally.

The pairing is what makes each half work. The standing objection to partitioners — that they remap everything at every LB step — costs nothing when run once, at the first step, where there is no incumbent to preserve. The standing objection to diffusion — that it is local, and slow to repair a globally bad assignment — is answered by handing it a good one to start from. Neither objection survives the combination.

The sequencing is already built

No new mechanism is needed to run one balancer once and another forever after. LBManager::nextLoadbalancer (LBManager.C:754-772) advances through the balancer list and then stays on the last entry:

currentLBIndex = seq + 1;
if (_lb_args.loop()) {
  if (currentLBIndex == loadbalancers.size()) currentLBIndex = 0;
} else {
  if (currentLBIndex == loadbalancers.size()) currentLBIndex--;  // keep using the last one
}

So the whole architecture is a command line:

./charmrun +p32 ./pic2d ... +balancer MetisLB +balancer DiffusionLB +LBCommOn
Do not pass +LBLoop. It flips the branch above to wrap-around, which would re-run METIS at every other LB step — the global remap this architecture exists to avoid. The absence of that flag is load-bearing; say so wherever the run command is documented.

One consequence worth stating: METIS runs at the first LB step, not at construction, so it partitions using measured load and a measured communication graph gathered while the application ran under DefaultArrayMap. That is what we want — it needs the graph, and the graph requires having run — but it means the first LB interval is spent on a bad mapping, and the reported "before" numbers belong to that mapping rather than to METIS.

What is genuinely comm-aware — and what isn't

MetricComm walks nodeStats->commData directly with the same filter ObjGraph uses — (!from_proc() && recv_type() == LD_OBJ_MSG) — and maintains per-object, per-neighbour structures:

std::vector<double> internalComm;               // internal comm for each obj
std::vector<std::vector<double>> externalComm;  // external comm for each obj for each nbor

The selection rule (DiffusionMetric.C:161-195) is: among available, migratable objects whose load fits the destination's remaining capacity, take the one with maximum externalComm[nbor][i] — send the object that already communicates most with the place it is going. That is the right rule, and it is the half of the design worth adopting.

The other half is disabled. DiffusionCore.C:78-80: 
nid = (nid + 1) % neighborCount;      // change to round robin for now
int nborId = nid;                     // metric->getBestNeighbor() is buggy (hangs)
Neighbour selection is round-robin. So load is offered to neighbours in arbitrary order and only the object choice is communication-aware. Any claim that "DiffusionLB is comm-aware" needs that qualification, and any measurement taken before getBestNeighbor is fixed is measuring a half-enabled strategy.

The GPU-awareness gap: four sites, one scalar

Every load decision in DiffusionLB reads host CPU time. The GPU dimension that this branch exists to collect never enters.

The work is one function, not five edits. Introduce a single objLoad(const LDObjData&) and route all five sites through it. What it returns is the open modelling question — max(wallTime, gpuTime), wallTime + gpuTime, or the α-blend that GPU_LB_PLAN.html Phase 2 describes — and routing everything through one function is what lets that question be answered later by changing one line rather than hunting call sites.

The fifth site is the worst of them: WithinNodeLB weighs resident objects by the floored getVertexLoad() (0.1 s each at pic2d granularity) and newly arrived objects by their shipped raw load (~10⁻⁴ s), then compares both against the same overLoad threshold. The heap will systematically shuffle residents while placing arrivals arbitrarily. Phase A's "reproduces original behaviour" test passes with this bug intact — it is original behaviour — so it is a Phase B item, and it is why Phase B cannot be skipped for CPU-only runs either.

Don't pick the scalar — ship both dimensions

Deferring objLoad()'s definition is right; deferring the protocol is not. The PseudoLoad exchange carries a single double today, so every future change to the load model is a protocol revision. Widen it once, now, before any consumers exist:

// PseudoLoad message payload, per node:
struct { double cpuLoad; double gpuLoad; double deviceFreeMem; };

Then the cross-node decision can be two-dimensional from day one, and the equalised dimension is chosen by measurement rather than baked in: under one process per device, cross-node is cross-device, so equalise summed gpuTime when the application is device-bound and per-PE CPU load when it is not — the Phase-2 α measurement in GPU_LB_PLAN.html already distinguishes the regimes. On pic2d, where objGPU is ~0.1% of step time, a gpuTime-equalising diffusion would chase noise; that is a property of the benchmark, not the design, and is why the validation matrix below leads with a device-bound workload.

deviceFreeMem rides along for the memory-capacity mechanism described under "GPU memory is a crash, not a constraint" below.

Two different load models are already running in the same loop. getVertexLoad() is MAX(compLoad, 0.1) (ckgraph.h:152). At pic2d's granularity every object sits below that floor, so the transfer accounting at DiffusionCore.C:101 sees every object as weighing exactly 0.1 s while the capacity filter at DiffusionMetric.C:172 reads real wallTime values three orders of magnitude smaller. The loop therefore decrements its budget in units it never checks against. Reconcile these before attributing any behaviour to the algorithm — this alone could explain erratic migration counts.

Node versus GPU group — do not restructure

Diffusion is node-level throughout: myNodeId, nodeSize, and transfers addressed as destPE = node * nodeSize. The GPU decision is per-device. The tempting move is to rewrite diffusion in terms of GPU groups. Don't.

Under one process per device — the precondition GPU_LB_PLAN.html already carries, and which holds on Delta at 4 processes × 8 PEs × 4 A40s — a Charm++ logical node is a GPU group, myNodeId is the device index, and the entire node-level algorithm becomes GPU-group-level with no structural change. Assert the precondition instead of engineering around it:

// In DiffusionLB setup: the two-level decomposition assumes one process per device.
// If a logical node's PEs span more than one device, the node-level diffusion
// is balancing across a boundary it cannot see. Detect and refuse.
for (pe in myNode) CkAssert(hapiDeviceForPe(pe) == hapiDeviceForPe(rank0PE));

CPU balance within a device across its 8 PEs is handled, but not where the code suggests. CascadingMigration is dead — its body is #if 0 (DiffusionLB.C:537) and its only call site sits inside a CkAbort branch. The live second level is WithinNodeLB (DiffusionLB.C:281): after cross-node migrations complete under quiescence detection, rank 0 heap-balances its residents plus the newly arrived objects across the node's PEs. Phase C's audit target is that function.

The two-hop delivery is free on the device — claim it, don't fear it. An object arriving cross-node lands on rank 0, then WithinNodeLB may migrate it again to its final PE. That second hop is same CmiNode and — under one process per device — same hapiDeviceForPe, so it takes emigrateIntraProcess (cklocation.C:3229-3237): raw pointer transfer, no PUP, no device copy. The expensive cross-node pull happens exactly once; the fix-up hop costs nothing on the device. The earlier open question about double device moves is resolved, in this architecture's favour — conditional on the one-process-per-device assertion above actually holding, which is one more reason to assert it rather than assume it.

GPU memory is a crash, not a constraint

For a central balancer, ignoring GPU memory produces a bad placement. For this pipeline it produces an abort: the destination's pull path allocates the incoming chare's device payload from the device LB buffer pool before issuing pulls, and hard-fails when the pool cannot hold it — immigrateGPUHandle's "Not enough memory on device Load balance buffer" CkAbort. popBestObject's capacity filter checks load only; no gpuAllocSize, no pool budget.

Diffusion makes this strictly worse than the central case, because the decisions are distributed: several overloaded nodes can independently select the same underloaded node in one LB step. Each transfer fits the destination's memory on its own; the sum aborts the run. A central LB can check a budget at assignment time — diffusion cannot, unless capacity is part of the protocol. That is what the deviceFreeMem field in the widened PseudoLoad message is for: each node advertises device headroom during the pseudo-LB rounds, senders decrement their local copy of it as they commit objects, and the round-trip nature of the pseudo rounds bounds the staleness. Conservative — headroom can be over-reserved, never over-committed.

Consequence for ordering: the memory phase moves before the first multi-node GPU measurement, not after the tuning phases. An LB experiment that can abort mid-run on a full buffer pool is not producing measurements, it is producing reruns.

Tier-aware neighbour selection

Diffusion's whole cost profile rides on which nodes are neighbours: load only flows along diffusion edges, and every edge is also a migration route. findNBors negotiates neighbours from the communication graph and object counts; nothing in it knows that two devices on the same physical node exchange load over an IPC pull (25–240 μs measured) while cross-node edges pay RDMA plus the staging synchronisation.

The fix reuses the transport tier table from COMM_AWARE_LB_PLAN.html a third time:

  • Seed, don't negotiate, the cheap edges. Every same-physical-node device pair becomes a diffusion edge unconditionally — on a 4-GPU node that is 3 free neighbours per node before the comm-graph negotiation runs, and it guarantees the cheapest transfer routes always exist regardless of what the MST finds.
  • Give the fixed getBestNeighbor() its tie-break. When Phase F revives comm-aware neighbour choice, equal-deficit neighbours should be ordered by tier — prefer shedding load across PCIe before shedding it across the network.

Making METIS the right step 0

METIS ships inside this tree at src/libs/ck-libs/metis/, so MetisLB builds with no external dependency. Two changes make it the right partitioner for this job.

1. Vertex weights are currently uniform

MetisLB weights vertices through ObjGraph, which means through getVertexLoad() and its 0.1 s floor. On this workload every vertex weight is identical, so METIS is doing pure edge-cut partitioning with no balance constraint whatsoever. For a step-0 mapping on an already-balanced application that is nearly harmless — and it is also not what anyone reading the code would assume. Give it the GPU-aware objLoad() scalar, bypassing the floor. Keep ncon = 1: multi-constraint partitioning across a CPU and a GPU dimension that differ by three orders of magnitude spends METIS's freedom satisfying a dimension that cannot affect runtime.

2. Flat partitioning cannot see the tier hierarchy

METIS k-way has no notion of heterogeneous link cost, so a flat partition into 32 parts prices a cross-device cut exactly like a cross-PE-within-device cut, when the two differ by roughly 28×. The fix does not require METIS to support anything it doesn't — partition twice:

// Level 1: nGpuGroups parts. Minimises the expensive cut -- across devices.
metisPartition(fullGraph, nGpuGroups);        // 4 parts on Delta

// Level 2: within each part independently, nPEsPerGroup parts.
// Minimises the cheap cut -- across PEs sharing a device.
for (g in groups) metisPartition(subgraphOf(g), nPEsPerGroup);   // 8 parts each

This encodes the transport hierarchy structurally rather than numerically, and it produces exactly the two-level assignment the rest of this effort is organised around. It is also strictly cheaper than one 32-way partition.

Part-to-PE remapping — the maximum-weight matching that keeps a partitioner from gratuitously relabelling — is unnecessary here. At the first LB step there is no incumbent worth preserving. This is the one place the standard objection genuinely does not apply.

Porting: cherry-pick the module, do not merge the branch

origin/diffusionlb forked from main in August 2024 and was last touched in May 2026; cupti_lb_reconverse carries CUPTI instrumentation, device migration paths, GPU groups, and reconverse. Merging the branch would drag 21 months of unrelated divergence. The nine Diffusion* files are a self-contained LB module and the Make.lb integration is purely additive, so cherry-pick the files.

Three things travel with them that are not files:

  • _lb_args.diffusionCommOn() does not exist on the target branch. It gates the entire comm-aware path (DiffusionCore.C:36); without it the build fails, and with it stubbed to false the strategy silently degrades to MetricCentroid. Port the argument alongside the code.
  • DiffusionLB never calls LBTurnCommOn(). Unlike every other comm-aware balancer in this tree, it relies on the user passing +LBCommOn. Call it from the constructor, as MetisLB.C:23 and the rest do — and note MetisLB already does, so the METIS step would work while the diffusion step silently saw an empty graph.
  • LDStats has changed since the fork — gpuPupSize, the user-data slot, and the CUDA-guarded fields. Expect the stats-shipping code in DiffusionCore.C:312-340 to need attention.

Algorithm improvements

Suggested after reading the implementation end to end. Ordered by value; the first two are correctness-at-scale rather than tuning.

1. Replace the MST with a ring backbone

The MST exists for exactly one reason: Phase 2 only converges if the neighbour graph is connected. A split graph converges to two different averages — permanently imbalanced, silently. Communication-derived neighbours do not guarantee connectivity on their own.

But a ring guarantees it far more cheaply: every node unconditionally adds (myNodeId ± 1) % numNodes, then fills its remaining k−2 slots with top-communication partners. Connectivity by construction, no rounds, no reduction, nothing to hang.

This deletes defect 3 rather than debugging it, deletes the degree-starvation half of defect 4, and removes an O(numNodes)-round protocol that currently re-runs on every LB step. The cost is two possibly-low-traffic edges per node — acceptable, because those are a fallback path for load flow; popBestObject still routes objects preferentially along high-affinity edges.

2. The "distributed" balancer is centralised through PE 0

Every phase transition is a hand-rolled barrier that fans in to PE 0: next_phase, next_MSTphase and pseudolb_barrier all count acks++ until acks == numNodes, via point-to-point messages — every pseudo-LB round. With ITERATIONS 40 that is 40 sequential O(N) fan-ins per LB step.

Invisible at 2 nodes; at 1000 nodes the decentralised balancer has a central coordinator with an O(N) inbox per round — 40,000 messages serialised through one scheduler per LB step — which is the bottleneck diffusion exists to avoid.

Anatomy of a round. Only two of the five steps are global:

1. send my_pseudo_load to each neighbour     -- neighbour-local, fine
2. when ReceiveLoadInfo x neighbourCount     -- neighbour-local, fine
3. PseudoLoadBalancing():
     send PseudoLoad to each neighbour       -- neighbour-local, fine
     thisProxy[0].pseudolb_barrier(allZero)  -- GLOBAL: O(N) fan-in to PE 0
4. when PseudoLoad x neighbourCount          -- neighbour-local, fine
5. when pseudoDone(bool)                     -- GLOBAL: broadcast back from PE 0

Those two exist for exactly one purpose: early termination. pseudolb_barrier ANDs every node's allZero flag and, if all nodes had nothing to send, pseudoDone(true) sets pseudo_itr = ITERATIONS to break the loop.

The obvious fix hangs. Replacing thisProxy[0] with contribute() reproduces defect 3 exactly: DiffusionLB is a group, so a group reduction needs every PE branch to contribute, and only rank-0 PEs execute PseudoLoadBalancing. Same participation mismatch that killed beginMST.

Three viable routes, in increasing order of how much they change:

  • Tree reduction, participation fixed. Either have non-rank-0 PEs contribute the AND-identity (allZero = 1) — which means driving them through a round loop they currently skip, more invasive than it looks — or build a CkSectionProxy over exactly the rank-0 branches once at neighbour-construction time and reduce over that. The section is the cleaner fit: participation matches by construction and non-rank-0 PEs are untouched. O(N) inbox becomes O(log N) depth, semantics identical.
  • Amortise the check. Diffusion converges monotonically, so checking 40 times to save a few rounds is a poor trade. Reduce only every K rounds (K ≈ 4–5): barriers drop 40 → 8 at a cost of at most K−1 wasted rounds. One guard on the contribute, composes with the above.
  • Delete the barrier. The loop is already for (pseudo_itr = 0; pseudo_itr < ITERATIONS; pseudo_itr++) — fixed at 40. The barrier's only job is early exit. Accept a fixed round count and Phase 2 becomes purely neighbour-local with zero global synchronisation. The cost is always paying the full count, but rounds move only doubles between neighbours, and with improvement 3 the count drops to ~7 — at which point deleting a distributed barrier to always run 7 cheap local rounds beats keeping one to sometimes run 5.

Recommended order: try deletion first behind a flag, since it removes the centralisation outright rather than making it cheaper. Only if measurement shows the early exit saves meaningful rounds on real workloads, fall back to section-reduction plus K-amortisation. Leave next_phase alone — it runs ROUNDS=20 times but only during neighbour discovery, and improvement 7 makes that rare.

Not testable here. At 2–4 nodes an O(N) fan-in and an O(log N) reduction are indistinguishable. This is a scaling fix and needs Delta, or at minimum a node count where the two separate, to demonstrate rather than assert. Deferred for that reason.

3. Second-order diffusion — the largest convergence win available

PseudoLoadBalancing is first-order: move load proportional to the deficit against the neighbourhood average. That is Jacobi iteration, and load crosses one hop per round.

The published fix is second-order over-relaxation (Diekmann, Frommer & Monien) — momentum on the flow:

flow[nbor] = beta * firstOrderFlow(nbor) + (beta - 1) * prevFlow[nbor];

Same relationship as SOR to Jacobi. On mesh-like graphs it cuts round counts by roughly a square root — 40 first-order rounds ≈ 6–7 second-order. A few lines, plus one previous-flow vector per neighbour. It compounds with improvement 2, because the rounds are precisely what carries the PE-0 barrier. β wants tuning against graph eigenvalues, but a fixed β ≈ 1.4–1.6 beats first-order on anything non-pathological.

4. Pay quotas best-fit, not first-fit

Phase 2 produces continuous quotas; Phase 3 pays them with discrete objects under objLoad <= nborCapacity, taking the highest-affinity object that fits. Two consequences: a quantisation residue — owing 0.04 s while holding only 0.05 s objects pays nothing, and the imbalance survives the step — and comm affinity strictly dominating load fit.

Better: among high-affinity candidates pick the one minimising |remainingQuota - objLoad|, and permit bounded overshoot (~25% of quota). Overshooting slightly and letting the next round pull it back is how continuous diffusion is meant to behave. This directly caps how balanced the result can be, so it is cheap value.

5. Amortise migration cost — diffusion needs this more than a central LB does

Diffusion migrates small amounts frequently, which is its nature; so "does this move repay itself before the next LB step?" bites harder here than for a balancer that moves rarely. There is currently no cost test — any positive quota triggers migration.

Apply the epoch rule from GPU_LB_PLAN.html: move only when epochIterations * perIterationGain > migCost(gpuPupSize, tier). Negligible for CPU-only lb_test; decisive for GPU chares with MB payloads, where an object near a quota boundary can otherwise be diffused back and forth on alternating steps. The cheap version is hysteresis: do not migrate an object that arrived within the last LB step unless the gain doubles.

6. Migrate once, not twice

Cross-node objects migrate to the destination's rank 0, then WithinNodeLB migrates them again to a final PE. Under one process per device the second hop is the free intra-process pointer handoff, but the first hop's destination choice is wasted and each migration is a real PUP plus a location-manager epoch. Restructure so LoadMetaInfo records the incoming object, WithinNodeLB chooses its final PE first, and a single Migrate(handle, finalPE) is issued from the donor. One migration per cross-node move, and no transient where rank 0 hosts everything.

7. Persist the neighbour graph across LB steps

Strategy() rebuilds neighbours from scratch on every invocation, running the full discovery protocol each time — but a stencil or mesh application's communication pattern barely changes between steps. Cache sendToNeighbors and rebuild only when the observed communication distribution shifts materially (say, the external/internal ratio moves more than a set percentage). Converts the per-step cost from "full protocol" to "nothing".

If two are implemented first: the ring backbone (1), because it removes the MST hang rather than debugging it, and best-fit quotas (4), because it is small and its absence bounds achievable balance. The GPU-specific items — two-scalar pseudo-load, deviceFreeMem advertising, tier-aware neighbour seeding — are already covered in their own sections above and are not repeated here.

Measured outcomes and the percolation decision

What happened when the improvements met measurement, and the design decision that resolved the open questions. 2026-08-21.

Improvement 1: implemented, kept

The ring backbone is in (buildRingBackbone, DiffusionNeighbors.C). Binary result, immune to noise: the default flags used to hang in MST construction and now complete with migrations at 2 and 4 nodes — including at the previously-fatal default diffusionNumNbors = 1, because the ring ignores the neighbour cap. Connectivity is not negotiable, so it shouldn't be capped.

Improvement 4: implemented, measured, rejected

Best-fit quota payment made things worse, twice over. With 25% overshoot the balancer churned ~6 objects per step and never settled — diffusion re-corrects every round by construction and does not need permission to overshoot; giving it that permission creates oscillation. With overshoot removed, five-run means at 4 nodes: first-fit 1.058 max/avg (spread 0.043), best-fit 1.079 (spread 0.109). Slightly worse and 2.5× more variable. Reverted.

The measurement lesson outlived the change. The first single-run A/B pointed the opposite direction from the five-run means. lb_test derives load from busy-wait calibration on a laptop, and its run-to-run variance is comparable to the effect sizes under test. Every balance-ratio claim needs n≈5 runs and a mean; integer results (round counts, migration counts, hang-vs-complete) are the only single-run-trustworthy measurements here.

Rejected designs for the >1000-node target

  • Dimension exchange (hypercube pairwise averaging, log₂N rounds, provably balanced): optimises rounds-to-equalise, but the partner schedule is index-based — quotas point at nodes the objects have no affinity for, and object-level comm-awareness cannot rescue a topology-level mistake. Wrong objective.
  • Long-range chords (ring + power-of-two offsets, log-diameter): every chord migration exiles a chare to a node it shares no communication with — a per-iteration cost paid forever to buy a per-LB-step convergence saving. This is the pic2d regression's shape. Mitigations exist (compute-dominant passengers only, ship connected clusters, affinity-based homing), but the decision was to not need them.

The decision: no-jumps diffusion

No jump edges — but convergence is still wanted. The topology is comm edges plus ring, full stop; a quota can therefore only ever point at a node the objects have a reason to be near, and every migration is one hop. Convergence of the pseudo phase is a separate matter and is kept: quotas are numbers, and numbers flowing A→B→C through the graph exile nobody. When the pseudo phase converges, the multi-hop transport is realised as a chain of simultaneous one-hop migrations — A pays B with A's objects while B pays C with B's — so most of a hot region drains in a single LB step, every move local and affinity-scored. What rolls over to later steps is only the residue: a lightly-loaded conduit node that cannot forward as much as flows through it, and quantisation. The thing being refused is exactly one thing: moving a chare to a non-communicating node to buy convergence speed. Convergence may cost extra rounds of cheap number-passing; it may never cost locality.

Why β=1.5 lost, and why that was predictable. The optimal over-relaxation factor is β_opt = 2 / (1 + √(1 − μ²)), where μ is the subdominant eigenvalue of the first-order iteration — the per-round survival factor of the smoothest imbalance the graph can hold. That formula is exactly where the SOR discriminant vanishes, so β_opt is the critical-damping point: below it, slower monotone approach; above it, oscillation with modulus β−1.

μ depends on the graph, so β_opt does too. On an N-ring with step size α the Laplacian eigenvalues are 2 − 2cos(2πk/N), giving μ = 1 − α·(2 − 2cos(2π/N)):

  • N = 4 (α ≈ 1/3): μ = 1/3, so β_opt ≈ 1.03. The graph mixes so fast that the right amount of momentum is essentially none — first-order already converges long before the round cap. β = 1.5 is far past optimum, which is precisely the regression measured.
  • N = 1000: μ ≈ 0.99999, so β_opt ≈ 1.99. Here momentum is the difference between converging and not.

So the default of 1.0 is not a fallback — at this node count it is within 3% of theoretically optimal. A hardcoded 1.5 would have been wrong at both ends, which is why β is a runtime knob (+LBDiffusionBeta) rather than a constant.

The ~1.06 plateau is quantisation, not convergence

Every configuration lands near 1.06, including ones the linear theory says should reach 10⁻¹². That floor is object granularity: 64 objects over 8 PEs is 8 per PE, so one object is ~12.5% of a PE's load and a half-object misfit is ~6%. 1.058 and 1.060 are sitting on it. No value of β fixes discreteness, and the residue that survives even at β=1.5 comes from the implementation's nonlinearities — the 1% threshold zeroing small flows, the leftToSend clamp truncating boosted sends, the negative-edge offsetting — not from oscillation. Further pseudo-phase tuning buys nothing at this problem size; the binding constraint moved downstream.

Dynamic β: specified, deferred to ≥32 nodes

β_opt must scale with the graph, and μ is measurable from the iteration's own behaviour — the diffusion process is a power iteration, so the global load variance decays as μ2k:

mu   = (Var_R / Var_S) ^ (1 / (2*(R - S)))       // sample at rounds S~5 and R~30
beta = clamp(2 / (1 + sqrt(1 - mu*mu)), 1.0, 1.95);

Var needs Σ L and Σ L² — one reduction, two doubles, sampled twice per LB step. That is 2 global operations against the 80 (2 × 40 rounds) just deleted, and unlike the barrier its value grows with N. Reuse β across LB steps; topology is stable between them.

Three practical rules: sample from round ~5, not 0, since the error only decays as a clean power law once it aligns with the dominant eigenvector; bias μ low, because underestimating gives β below optimum (slower but monotone) while overestimating gives genuine oscillation; and skip the update when Var_R is at the threshold floor, where the ratio is noise.

Not buildable here. Below ~32 nodes the correct answer is β = 1.0, which is already the default — an estimator whose right answer is the value you already have cannot be validated. Build it where the slow-mixing regime exists.

Defects to expect in the diffusion code

Beyond the five found in Phase A. Research code with visible rough edges; none disqualifying, all worth knowing before debugging behaviour that looks algorithmic.

  • getBestNeighbor() hangs and is bypassed by round-robin — the neighbour half of the comm-awareness is off. Note this is a second broken neighbour routine, independent of defect 3.
  • objAvailable[bestObject] = false is commented out in popBestObject (DiffusionMetric.C:184-188), so the same object can be selected repeatedly unless updateState covers it. Verify that it does.
  • int testComm = externalComm[nbor][i] truncates a double byte-count to int — both a precision loss and a re-entry of the overflow hazard already documented for LDCommData::bytes.
  • memset(gain_val, 100, n_objs) sets n_objs bytes of an int array to 0x64. The gain-value machinery appears unused (buildGainValues and InitializeObjHeap are commented out), so this is likely dead — confirm before relying on it.

Validation

The benchmark matrix was inverted — lead with the device-bound workload. pic2d is already balanced and its GPU fraction is ~0.1% of step time: it can only ever prove "did not get worse." The demonstration workload needs genuine imbalance with a dominant GPU dimension, and one is already built in this tree: examples/charm++/cuda/gpudirect/jacobi2d-imbalance. Primary benchmark for Phases B and D; pic2d becomes the regression benchmark it was always suited to be.
  • Phase A: DiffusionLB on cupti_lb_reconverse reproduces its behaviour on origin/diffusionlb for a CPU benchmark. Migration counts and load summaries should match.
  • Phase B: confirm gpuTime actually differentiates objects on jacobi2d-imbalance — and confirm it does not on pic2d, which is the measured justification for equalising the CPU dimension there instead. Phase 1's lesson was that a load dimension worth 0.1% of step time cannot drive a balancer.
  • Phase D, the headline: pic2d iteration time against the two established numbers — 13.4 ms with migration disabled, ~20 ms with GreedyRefineCentralGPULB. The target is to beat the first, not merely the second.
  • Locality, using their metric: print_internal_comm / print_external_comm are already in the code, and the external/internal ratio is the quantity the published GreedyRefine-versus-diffusion comparison reports. Using the same metric makes our numbers directly comparable to theirs rather than merely internally consistent.
  • Regression: a genuinely imbalanced run must still migrate. Diffusion that converges to doing nothing is indistinguishable from success on pic2d, which is already balanced.

Open questions

  • destPE = node * nodeSize assumes uniform node size. Is that safe under the launch configurations we use?
  • Heterogeneous devices: when nodes carry different GPUs, the pseudo rounds should equalise gpuLoad / capacity rather than raw load. ProcStats::gpu_total_sms is already collected and is the natural capacity denominator — one more field the widened PseudoLoad message can carry, but only worth it on machines we actually target.
  • Is the PDSEC paper's implementation this branch, or a descendant of it? Worth resolving, because if it is, its reported numbers are a baseline we can reproduce rather than a claim we have to trust.
  • Does METIS's step-0 partition survive the first diffusion step, or does diffusion immediately undo it? The two optimise related but not identical objectives, and nothing currently prevents the second from discarding the first.
